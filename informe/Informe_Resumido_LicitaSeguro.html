1. El caso y la solucion

LicitaSeguro entrega informacion sobre licitaciones publicas, pero no tiene portal propio: todas sus busquedas se hacen dentro de Mercado Publico, una plataforma pensada para compradores del Estado y no para la consulta rapida. La solucion desarrollada es un sitio web publico de cuatro vistas que consume en linea la API oficial de Mercado Publico y presenta la informacion de forma ordenada, responsiva y accesible. El sitio no almacena ni modifica datos.

VistaArchivoFuncion
1. Homepageindex.htmlPresentacion corporativa, acceso a los 3 modulos y formulario de contacto validado.
2. Listadolicitaciones.htmlFiltros por fecha y estado, loader, tarjetas de resultado y paginacion de 10 en 10.
3. Detalledetalle.htmlFicha completa de una licitacion a partir de su codigo.
4. Proveedoresproveedores.htmlBusqueda de proveedor por RUT con validacion modulo 11.

Tecnologias: HTML5 semantico, CSS3 con variables y media queries propias, JavaScript ES6 puro (modulos IIFE, async/await, fetch, AbortController) y Bootstrap 5.3.3 por CDN para grilla y componentes.

3. Tarea 1: Mockups y decisiones UI/UX

Se elaboraron cuatro mockups (uno por vista), cada uno dibujado en laptop 1366px, tablet 768px y movil 375px, con su justificacion incorporada. Archivos completos en informe/mockups/.

Color y contraste

Azul institucional #0b3c5d (confianza, sector publico) con naranja #f2a65a solo como acento de foco. Todas las combinaciones se verificaron con el comprobador de WebAIM y quedaron documentadas como comentario en css/styles.css:

Ningun estado se comunica solo con color (WCAG 1.4.1): los badges escriben siempre la palabra ("Estado: Publicada") y las alertas llevan icono y titulo.

Tipografia y espaciado

Familia Segoe UI / system-ui, sin serifa, disponible en el sistema (sin descargas externas). Escala modular de razon 1.25: H1 31px, H2 25px, H3 20px, cuerpo 16px, textos de ayuda 14px. Interlineado 1.6 (WCAG 1.4.12) y ancho de lectura limitado a 75 caracteres. Todo el espaciado es multiplo de 8px y los elementos interactivos miden al menos 44x44px (WCAG 2.5.5).

Usabilidad (heuristicas de Nielsen aplicadas)

  • Visibilidad del estado: loader con texto y resumen "Mostrando 1 a 10 de N licitaciones. Pagina X de Y".
  • Prevencion de errores: fecha con input type="date" y atributo max; estado como select cerrado; RUT formateado mientras se escribe.
  • Consistencia: mismo header, footer, paleta y estilo de tarjeta en las 4 vistas.
  • Control del usuario: "Limpiar filtros", "Volver al listado" y migas de pan.
  • Recuperacion de errores: cada mensaje explica la causa y la correccion ("el digito correcto es 3"), nunca un generico "dato invalido".

5. Tarea 3: Validaciones, loader y paginacion

Todos los formularios usan novalidate: la validacion nativa se desactiva para controlar desde JavaScript el idioma, el momento y la ubicacion del mensaje. Cada error se escribe en un span ubicado bajo el campo, asociado por aria-describedby, con role="alert", y el campo recibe aria-invalid="true" mas borde rojo: el error se percibe por texto, color y semantica.

Loader

Aparece antes de lanzar la peticion, deshabilita el boton que la origino y bloquea la zona de resultados con pointer-events:none; se oculta en el instante en que la respuesta fue procesada, tanto si hubo exito como error. Declara role="status" y aria-live="polite". 

UI.mostrarLoader(ID.loader, { bloquear: ID.resultados, boton: ID.boton });
const respuesta = await API.obtenerLicitaciones(fecha, estado);
UI.ocultarLoader(ID.loader, { bloquear: ID.resultados, boton: ID.boton });

Paginacion

La API devuelve todas las licitaciones del dia (por ejemplo 4.503), de modo que la paginacion se resuelve en el cliente con slice() sobre el arreglo guardado en el estado de la vista. Constante ITEMS_POR_PAGINA = 10; si hay 10 o menos resultados la paginacion no se dibuja; "Anterior" queda deshabilitado en la primera pagina y "Siguiente" en la ultima; la pagina activa se marca con aria-current="page"; al cambiar de pagina el foco vuelve al resumen de resultados. Un unico listener delegado atiende todos los botones.

6. Tarea 4: Validacion del RUT y endpoints

Algoritmo modulo 11 implementado en js/validaciones.js:

function calcularDigitoVerificador(cuerpo) {
  let suma = 0, multiplicador = 2;
  for (let i = cuerpo.length - 1; i >= 0; i--) {          // de derecha a izquierda
    suma += parseInt(cuerpo.charAt(i), 10) * multiplicador;
    multiplicador = multiplicador === 7 ? 2 : multiplicador + 1;  // serie 2..7
  }
  const resto = 11 - (suma % 11);
  if (resto === 11) return '0';
  if (resto === 10) return 'K';
  return String(resto);
}

El campo se formatea solo mientras se escribe, porque el endpoint exige el RUT con puntos y guion.

#FuncionEndpoint
1ListadoGET /servicios/v1/publico/licitaciones.json?fecha=ddmmaaaa&estado=nombre&ticket=cod
2DetalleGET /servicios/v1/publico/licitaciones.json?codigo=1057539-17-LR25&ticket=cod
3ProveedorGET /servicios/v1/Publico/Empresas/BuscarProveedor?rutempresaproveedor=77.653.382-3&ticket=cod

El encadenamiento es el indicado en el documento de apoyo: del listado se obtiene el CodigoExterno, que viaja por la URL a la vista de detalle para consultar el segundo endpoint; el tercero se consulta aparte con el RUT ya validado.

10. Ejecucion del proyecto

Es un proyecto estatico, pero debe abrirse con un servidor local: los navegadores bloquean fetch desde el protocolo file://. 

cd Eval_U3A_LicitaSeguro
python3 -m http.server 8080
# Abrir http://localhost:8080/index.html

El ticket de la API esta en js/config.js (constante TICKET).

11. Conclusiones

Es posible construir una aplicacion frontend util y de mediana complejidad con solo HTML, CSS, JavaScript y un framework CSS. La organizacion en capas fue determinante: permitio reutilizar la validacion del RUT y el manejo del loader en varias vistas, y concentrar todo el control de errores de la API en un solo archivo.

La mayor dificultad tecnica fueron los datos de Mercado Publico: campos nulos, textos en mayusculas y caracteres mal codificados. Eso obligo a construir una capa de normalizacion previa al renderizado, lo que confirma que consumir un endpoint no se agota en obtener la respuesta, sino en validarla y presentarla de forma confiable. En accesibilidad quedo claro que no es un agregado final: contraste, jerarquia de encabezados, orden de tabulacion y manejo del foco se definieron desde el mockup, evitando rehacer la interfaz al terminar.
